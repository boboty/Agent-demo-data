# BrewGo G2 竞品对比 Listing 优化任务

## 业务目标

根据用户在当前对话中提供的 Amazon US 搜索关键词，在线发现相关候选商品，核验商品详情中的 Best Sellers Rank（BSR），在同一具体类目内筛选 BSR 数值最靠前的 5 个产品。先把拟采用结果发回对话，请用户确认；只有确认后，才能继续分析并把数据写入 HTML 展示页。

工作顺序应为：关键词 → 在线发现候选 → 核验 BSR 与具体类目 → 同类目筛选前 5 → **在对话中请求用户确认并暂停** → 用户确认 → BrewGo 核验与竞品分析 → 生成 HTML 展示页。不要要求用户粘贴搜索页、商品页或任何 HTML。

## 两阶段交互

### 阶段一：检索与确认

用户给出关键词后，在线检索并在对话中展示拟采用的最多 5 个产品。确认表至少包含：排名、品牌、商品标题、ASIN、BSR 数值、BSR 具体类目、商品 URL、证据状态和访问时间。

同时说明：

- 使用了哪个具体类目及原因；
- 排除了哪些重复、跨类目或无法核验 BSR 的候选；
- 如果不足 5 个，为什么不能补齐。

然后明确询问用户是否确认使用这组产品。此时必须停止，不得生成分析结论，不得写入 `outputs/`，也不得默认用户同意。用户调整产品或类目后，应更新确认表并再次确认。

### 阶段二：确认后生成 HTML

只有用户明确确认候选产品后，才读取 BrewGo 资料、完成竞品分析和 Listing 优化，并将确认后的数据与分析写入 `outputs/competitor-analysis.html`。使用工作区自带的 `report-template.html` 作为展示模板，不覆盖模板本身。

## 输入与证据层级

- `input/product_profile_g2.md`、`input/products.xlsx`：BrewGo 产品事实来源；SKU、变体和产品能力以这些资料为准。
- `input/reviews.csv`：BrewGo 用户场景与体验线索；评论不能单独证明产品能力、缺陷原因或定量性能。
- `input/listing_current.md`：待优化草稿，不是产品事实来源。
- 用户输入的关键词：候选发现入口，不是商品表现证据。
- Amazon 搜索结果页：用于发现候选商品；自然位、Sponsored 位或展示顺序均不等于 BSR。
- 可访问的 Amazon 商品详情页或其他能够直接核验该商品 Amazon BSR 的页面：用于记录 ASIN、完整 BSR 数值、具体类目、URL 和访问时间。
- 竞品 Listing：竞品卖方自我声明，用于观察定位、卖点结构和表达策略。
- 竞品 Review：竞品用户体验线索；不能自动证明 Listing 声明或产品性能。
- `business/` 与 `project-context.md`：长期业务规则、事实边界和人工确认原则。

在线竞品资料只用于市场和表达观察，不能作为 BrewGo 产品事实来源。竞品 Listing、Review 和 BSR 也不能自动视为同等级证据；BSR 不是销量件数。

## BSR 筛选规则

1. 先收集足够多的关键词相关候选，再逐一核验商品详情中的 BSR。
2. BSR 必须同时保留数值和完整具体类目，例如 `#12 in Manual Coffee Grinders`；不得只摘录数字。
3. 只在相同具体类目内按 BSR 数值升序筛选。不同类目不得混排；需选择与 BrewGo G2 最相关、且有足够可核验候选的具体类目，并说明选择依据。
4. 去除 Sponsored 重复、同一 ASIN 重复和明显不相关产品；Sponsored 身份本身不影响是否可作为候选，但不能把广告位置当排名。
5. 不能把搜索结果顺序、评论数、评分或第三方销量估算冒充 BSR。
6. 如果同一具体类目中不足 5 个商品具有可核验 BSR，只分析实际核验数量，并列出缺口；不得跨类目或用未知值凑满 5 个。
7. 所有在线事实记录来源 URL 和访问时间；页面无法访问或字段不可见时明确标记，不猜测。

## 约束

1. 不得虚构 BrewGo 的产品能力、规格、性能、配件、兼容性或比较结论。
2. 不得把竞品的 USB-C、档位数量、高转速、易拆洗或其他能力迁移成 BrewGo 能力。
3. 不得复制竞品 slogan、完整 Bullet 或具有识别度的独特句式；可以学习定位方法、内容组织和卖点结构。
4. 所有重要修改必须说明证据来源和判断依据，并区分产品事实、用户线索、竞品自我声明和竞品体验线索。
5. 主观评论不得扩展成未经验证的分贝、百分比、速度、续航或优于竞品等定量声明。
6. 当前 Listing 中已有说法也必须与 BrewGo 事实核对；发现不实能力时应在最终建议稿中移除，但不要把全部工作退化为逐项查错。
7. Listing 发布属于人工确认动作；本任务只生成建议文件，不执行发布或其他外部业务动作。
8. 用户确认是写入 HTML 的硬门槛；“继续看看”“先分析一下”或沉默不能视为确认。

## 输出

用户确认前，`outputs/` 必须保持为空。用户确认后，只创建：

### `competitor-analysis.html`

复制 `report-template.html` 的结构和样式，将页面内的 `REPORT_DATA` 替换为本次确认后的数据。不得依赖 CDN、远程脚本、远程字体或联网才能工作的资源。页面至少展示：

- 关键词、检索时间、确认时间、采用的 BSR 具体类目和筛选说明；
- 确认后的最多 5 个产品及其 ASIN、BSR、类目、URL 和证据状态；
- BrewGo 与竞品的比较矩阵；
- 优化机会，每项包含竞品观察、BrewGo 证据、证据等级、是否可用于 Listing、建议动作和风险边界；
- 优化后的 Title、5 Bullets、Product Description 和 Backend Search Terms；
- 重要变更的“原文 → 修改 → 依据 → 风险处理”；
- 数据局限、人工确认项和所有来源链接。

`REPORT_DATA` 必须是合法 JSON，可由页面内置脚本渲染；将在线文本作为纯文本显示，不拼接为可执行 HTML。页面标题和正文应清楚标注这是待人工审核的分析，不代表已经发布 Listing。

## 完成前检查

- 用户确认前没有写入任何业务输出。
- 用户确认后只有 `competitor-analysis.html`，且可离线打开、内容完整。
- BrewGo 的关键说法可以追溯到 BrewGo 事实或明确标注的评论线索。
- 竞品确由同一具体类目的可核验 BSR 选出；若不足 5 个，缺口已说明。
- 没有迁移竞品能力，没有复制竞品文案，没有制造定量比较声明。
- 已区分“另一种定位机会”和“缺失竞品能力”。
- 输出中没有发布、改价或其他未经授权的外部动作。
