# 预期观察与讲解分支

## 三阶段统一概括

- Demo 01：**一句话，自由度主要由 AI 自己补齐。**
- Demo 02：**人把这一次任务定义清楚。**
- Demo 03：**把跨任务长期有效的规则沉淀进工作环境，然后又只需一句话。**

统一课堂概括：

> **同一个 AI，同一件事，三种交办方式。**

> **前三轮没有换 AI，真正变化的是 AI 周围的工作环境。**

## 稳定结论

- 一句话任务能够启动真实工作，但输入范围、输出结构和验收责任较隐含。
- 任务卡在数据基本不变时提高交付的完整性、可追溯性和可验收性。
- 项目上下文适合承载跨任务复用的事实位置、业务边界和人工确认原则。
- 工作区规则不能代替事实数据；漂亮文案也不能代替证据。

## Demo 01 可能波动

智能体可能只读 Listing，也可能主动读取全部资料；可能发现多数事实冲突，也可能主要做文案润色。两者都可用于讨论自然指令没有明确资料范围、交付结构和验收标准。

如果结果很好，检查依据是否完整、结构是否稳定；如果结果较弱，指出具体遗漏，但不要把弱结果解释为模型必然无能力。

## Demo 02 可能波动

建议稿措辞和问题排序仍会变化，但三类交付、事实核对和人工确认项通常更完整。若仍遗漏，直接以讲师粘贴的任务卡验收条目复核，这正是结构化定义的价值。

如果 Demo 02 与 Demo 01 差异不大，区分"文案质量相近"和"过程更可检查"：文件齐全、依据清楚、风险单列本身就是业务质量提升。

## Demo 03 可能波动

长期规则不保证每次生成固定答案，但应提高规则发现和应用的一致性。某次 Demo 02 也可能主动做得很好；此时比较换任务、换会话后是否仍能稳定遵守相同规则。

如果项目上下文造成输出过度保守，可讨论规则是否清楚地区分"禁止执行"和"允许提出建议"，而不是删除人工确认边界。

## 不应依赖的剧情

- 不要求智能体必须保留某个错误说法。
- 不要求每次命中完全相同的问题数量。
- 不要求建议稿逐字一致。
- 不把单次表现推广为某个工具的永久能力结论。

课堂观察应记录实际文件、依据和验收结果，再解释不同表现。

## Demo 06 稳定观察

- 应根据对话关键词在线发现候选，区分搜索位置和 BSR，并只在同一具体类目内排序。
- 应先把最多 5 个拟采用产品发给用户确认，在明确确认前暂停且不生成 HTML。
- 应把竞品 Listing 识别为卖方自我声明，把竞品 Review 识别为体验线索；二者都不是 BrewGo 产品事实。
- 应拒绝把在线竞品的 USB-C、档位数量、高转速或电动能力迁移给手摇的 BrewGo G2。
- 应从 BrewGo 评论与事实资料中发现 travel、carry-on、office、single-cup 场景，并判断当前 Listing 对这些场景的表达仍可强化。
- 应发现 BrewGo 的清洁评论含负面体验线索，因此不能安全写 `easy to clean`。
- 应允许得出反直觉结论：竞品的电动、多参数优势不自动构成 BrewGo 的缺点；手摇、无需充电和单杯便携使用可以形成不同定位。
- 确认后生成的离线 HTML 应完整展示数据集、证据、机会、Listing 和变更依据；Listing 应移除原稿中的错误产品能力。

## Demo 06 可能波动

智能体找到的产品会随时间、地区和页面可访问性变化，也可能不足 5 个。验收重点不是固定竞品或固定文案，而是 BSR 类目是否可比、确认门槛是否执行、证据是否足够、竞品能力是否被隔离以及 HTML 内部是否一致。

如果结果主要重复 Demo 01 的事实查错，应回到 HTML 的“优化机会”区检查是否真正完成了竞品观察 → BrewGo 核验 → 可用性判断。旧错误仍必须从最终稿移除，但不是本 Demo 的全部价值。
